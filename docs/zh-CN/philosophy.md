# 规则哲学

## 使命

Cynos Rules 向编程 Agent 教授可移植的判断，而不会把 System Prompt 变成工作流手册。

> **教授判断，而不是操作步骤。检验每一条规则。**

规则是假设。每条规则都必须通过可观察证据证明自己值得永久占用 Token。

## 产品边界

Runtime Rule 是简短、宿主中立的判断指导。它不是项目记忆、技术指南、模板库、Skill、完整工作流、工具 Policy 或安全控制。

仓库约定、框架偏好、固定目录布局、部署步骤、提交格式和组织专用流程不属于权威 Ruleset。

如果 formatter、linter、schema、hook、type checker、sandbox、权限边界或其他确定性机制能够更可靠地解决问题，就应使用该机制，而不是 Prompt 文本。

## 准入

候选规则需要同时满足以下条件：

1. 真实或可复现失败；
2. 现有规则没有覆盖的实质性判断错误；
3. 可观察的行为变化；
4. 能适用于不同仓库和技术栈；
5. 清楚的边界、禁止行为、停止条件或例外；
6. 正向、近邻、冲突和过度遵循测试；
7. 相对未改变 Baseline 的预注册比较；
8. 可接受的 Token、费用和回归影响。

除非被转换为具有证据、边界清楚且可观察的判断规则，否则“编写优雅代码”“始终深入思考”或“遵循最佳实践”等宽泛愿望都会被拒绝。

## 规则形式

优先使用：

```text
触发条件或状态
→ 判断边界
→ 可观察行为或禁止行为
→ 停止条件或例外
```

有用的规则会说明何时适用以及何时停止适用。它把任务专用实现选择留给 Agent 和项目上下文。

## 证据

定向 Fixtures 判断预期判断是否改变。真实 Issue 任务检验这种改善能否在现实编程工作中继续存在，同时不损害解决率、成本或范围。

更高的 Benchmark 分数本身不能证明单条规则。更低的分数本身也不能解释原因。应使用配对任务证据、检查回归，并诚实报告不确定性。

确认任务不是调优材料。一旦其中的 Finding 影响变更，就应在再次提出确认声明前退出已经暴露的集合。

## 上下文经济

System Prompt 空间是稀缺的共享资源。更短不一定更好，但每个词都必须为经过检验的判断边界作出贡献。应删除重复、不会改变解释的示例，以及 Pi 已经实现的指令。

包含身份 Marker 的完整 v0 注入块受到权威设计的限制。

## 权威与冲突

System 和宿主指令位于 Cynos Rules 之上。明确的用户要求和固定的项目上下文定义任务。Cynos Rules 不得声称对 Acceptance Decision、凭据、权限、隐藏测试或外部 Policy 具有权威。

Prompt Guidance 不能强制安全边界。容器、凭据、网络控制和官方 Evaluator 提供这些边界。

## 生命周期

通过普通 GitHub Issues 和 Pull Requests 添加、修改和删除规则。当证据表明规则没有收益、造成有害的过度遵循、成本过高、重复、过时或已被确定性能力替代时，应当修改或删除它。

目标不是积累规则。目标是保留仍然能够改善可观察判断的最小集合。

## 非目标

Cynos Rules 不以以下事项为目标：

- 编码所有软件工程实践；
- 替代测试、Review 或项目文档；
- 让所有模型行为完全一致；
- 保证正确性或合规性；
- 通过任务专用提示针对一个 Benchmark 优化；
- 成为通用 Agent 框架。
