# 需求文档写作方案

保留现有 intent/spec/plan 三文件结构，补充职责和写作边界，不增加模板文件或审批流程。

## 三份文档的分工

- Intent 让人确认用户想解决什么。保留原始诉求和明确补充，项目事实单独说明，AI 推断不冒充用户决定。
- Spec 让人判断方案是否合适。只展开本次新增或改变的关键方案、取舍和验收结果，已有约定简短引用；保留影响决策的安全、兼容和接口要求，逐项校验和测试矩阵进入 Plan。
- Plan 让 AI 能分阶段实施。每阶段说明目标、必要修改点、执行顺序和验证方法，按需补充依赖与风险，不重复 Spec。

## 写作要求

开头直接给出本文件的核心内容。栏目按需设置，不规定字数或阶段数量；同一事实只在负责的文件展开，通用规则通过引用复用。Plan 只简记当前进度、阻塞和证据位置，不变成执行日志。

保留一组虚构短正例，以及写前按读者问题筛选、写后删减的方法，不提供必填模板。按文件职责合并重复规则，不改变关键约束；成稿核对用户要求、条件、例外、风险和待定状态，不向用户附加写作过程。

## 验收

- 读者能区分用户要求、项目事实和 AI 建议；未确认事项既不被写成必做，也不被写成不做，相关实施步骤保留条件。
- 既能把内部函数、修改文件和测试命令放进 Plan，也不会把需求本身的公共接口、安全和兼容约定移出 Spec。
- 本次需求三文件示范上述分工，现有入口能引导编写和修改需求的 AI 读取新规则。
- 读者能从测试文档找到诉求、关键方案和第一阶段行动；不能只以字符数减少判定改善，也不能把正例的业务或实现选择搬入其他项目。
- 目录约定、已有历史文档和正式版本保持不变；本次变更只记为未发布。
