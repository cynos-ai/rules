# 将 Cynos Rules 收敛为可复制的项目规则

## 当前问题

现有仓库围绕 npm 包、Pi Adapter、规则 digest、Harbor 和付费 Benchmark 设计，远超“给项目安装一组基础 AI 工作规则和文件约定”的真实需要。它尚未正式发布，但维护成本已经很高，也只服务特定宿主。

同时，`~/文档/java-taro-rules/` 中已经存在一批直接、实用的工程规则。它们混有 Java、Spring、Taro 等技术栈内容，需要提取通用部分，而不是重新设计抽象规则体系。

## 期望结果

1. `cynos-ai/rules` 只保存 Markdown 规则和安装说明；
2. 用户可以把 README 中的一段提示词交给 AI，让 AI 为目标项目安装规则；
3. 支持 `AGENTS.md` 的平台使用该入口，不支持的平台由对应 AI 选择原生规则入口；
4. 规则包含通用开发行为、架构、安全、评审、项目文件和 Git 规范；
5. AI 可以在用户确认后整理旧文档，不丢失仍有效内容；
6. 目标项目记录已安装 Rules 版本，后续 AI 能比较版本后安全更新；
7. 旧 `java-taro-rules` 类规则作为 v0 迁移基线，其中仍有效的技术栈规则在升级时保留；
8. 旧 npm、Adapter 和评测实现停止维护并从当前版本删除。

## 受影响对象

- `cynos-ai/rules` 仓库维护者；
- 使用 README 提示词安装规则的项目负责人和 AI；
- 已有文档需要迁移到 Cynos 默认目录的项目。

## 约束

- 规则技术栈无关、直接、短小，不沿用旧项目的抽象注入语言；
- 不发布 npm 包，不实现安装脚本、CLI、SDK 或 Harness Adapter；
- 不覆盖目标项目已有规则；
- 不擅自移动、删除或归档目标项目文件；
- 正式/开发分支和基础分支类型属于默认规范，PR 是否强制由用户决定；
- 保留 MIT License 和旧方案 Git 历史；
- 版本机制只使用文本版本文件、Changelog 和 Git tag，不重新引入包管理器或安装程序。

## 明确不做

- 不保证各 AI 平台完全一致地加载规则；
- 不做规则自动同步、版本锁定或运行时强制；
- 不维护 Java、Taro 或其他特定技术栈模板；
- 不建设规则评测平台、Token 预算、Manifest 或模型 Profile；
- 不规定源码目录结构。
