# 完成边界与沟通检查方案

承接 [需求写作规则](../requirement-document-clarity/spec.md) 的三文件分工，补充完成后的边界；沿用 [日期命名约定](../2026-09-07-change-directory-dates/spec.md)，不迁移历史目录。

## Change 完成边界

实施期间可在当前范围内修订原 change。该范围的实施及必要验证全部完成时，在 Plan 记录完成结果；此后三文件保留为历史，不再改写。代码或部分阶段完成、必要验证仍未完成，不等于整个 change 完成。

后续新增、调整及缺陷修复新建 change，引用原 change 并说明承接内容和本次差异，不向旧 Plan 追加阶段或重写旧 Spec。完成后的提交、合并与发布事实保留在 Git、PR、Release 中，不回填原 change。

开发行为规则在修改前引用这项判断，让修 Bug 等后续任务也先核对原 change 的完成状态，而不只在编写文档时读取。

## 简洁表达检查

继续使用现有 [沟通规则](../../rules/communication.md)，不新增模板或禁令。检查实际回复及相邻上下文，删掉重复结论和没有新增信息的过程播报，同时保留重要失败、未验证项和需要用户决定的问题。

只评估抽取的样本；原回复、改写建议和独立复核分开保存，不把建议稿的表现当成本助手已稳定遵循规则的证明。
