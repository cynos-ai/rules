# 通用沟通与简洁表达规则规格

## 1. 适用范围

`docs/rules/communication.md` 默认适用于所有面向用户的自然语言回复，包括直接回答、澄清问题、解释、建议、方案、状态、进度、故障和完成报告。

以下内容遵循自身格式和受众要求，不强制套用聊天表达结构：

- 代码、配置、命令和精确引用；
- 正式文档、报告、邮件和第三方消息；
- Commit、PR、Issue、缺陷和评审意见；
- 用户明确指定格式、语气或详细程度的产物。

## 2. 默认表达

- 使用用户当前主要语言，保留准确的行业术语；
- 先给直接答案、判断或用户可观察结果；
- 只补充理解和行动所需的原因，再按需给证据与实现细节；
- 删除寒暄、填充词、重复总结、无信息的小标题和无价值的工具过程叙述；
- 同一事实只表达一次，不为显得完整而机械套模板；
- 保持正常、专业、易读的语法；不模仿 Caveman 品牌语气，不发明缩写，也不以破碎句式制造简洁感。

## 3. 信息组织

- 简单问题直接回答；没有必要时不增加背景、标题或下一步；
- 一般说明先给结论，再给二至四个必要理由，可选深度放在后面；
- 项目和架构说明按用户可观察行为、概念职责与流程、影响或取舍、必要实现证据的顺序展开；
- 方案与建议先给推荐，再说明关键理由、主要取舍和仍需用户决定的事项；
- 状态与完成报告先说结果，再说验证、未解决风险和必要定位；
- 故障说明先说现象与影响，再区分已确认原因和当前推断，最后说明状态与下一步。

这些是按场景选用的组织方式，不是每次回答都要填满的固定模板。

## 4. 精确性与清晰度

压缩文字时不得删除或模糊：

- `不`、`仅`、`除外` 等会改变含义的限定；
- 条件、顺序、前置要求和失败后果；
- 数字、单位、版本、日期、路径、命令、标识符和精确错误；
- 安全、数据丢失、不可逆操作和材料成本警告；
- 事实、推断、建议、未知项和阻塞项之间对行动有影响的区别。

安全警告、不可逆确认、顺序敏感的多步操作或用户已经表示困惑时，清晰度优先于简短。若压缩后的表达并未更短或更容易理解，使用正常完整表达。

## 5. 入口与版本

- 根 `AGENTS.md` 把所有面向用户的自然语言沟通路由到 `docs/rules/communication.md`；
- `AGENTS.md` 同时保留一句常驻底线，确保没有额外读取时也先给答案并避免无用过程叙述；
- README、项目文件树和安装内容加入 `communication.md`；
- `docs/rules/VERSION` 更新为 `1.1.0`；
- `CHANGELOG.md` 说明本次新增及其与 Guidance/Caveman 的边界；
- 合入 `main` 后创建 Git tag `v1.1.0`。

## 6. 验收条件

- **AC-SCOPE-01**：communication 默认覆盖大部分用户沟通，同时明确正式产物边界；
- **AC-DIRECT-01**：规则要求先给答案或结果，并删除填充、重复和无价值过程叙述；
- **AC-STRUCTURE-01**：规则覆盖简单回答、一般说明、项目解释、建议、状态和故障的按需组织；
- **AC-CLARITY-01**：否定、条件、数字、精确技术内容和高风险警告不因简洁而丢失；
- **AC-NONMODE-01**：没有引入对话工作流、强度模式、Skill、Adapter 或运行时；
- **AC-ENTRY-01**：AGENTS、README 和项目文件树均能定位 communication；
- **AC-VERSION-01**：VERSION、Changelog 和发布 tag 一致为 `1.1.0`；
- **AC-READER-01**：无上下文 AI 能正确区分聊天输出与正式产物，并生成简洁但完整的回复。
